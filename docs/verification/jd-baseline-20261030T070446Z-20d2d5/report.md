批次：`jd-baseline-20261030T070446Z-20d2d5`。北京时间约 15:04–15:07 执行。测试进程正常退出，临时 HTTP 服务已停止。未调用真实模型，未修改业务代码或现有业务数据库。

## 方法与隔离

- 使用 backend/.venv/Scripts/python.exe 执行 backend/scripts/jd_load_baseline.py。
- 独立 synthetic.db，由当前 ORM create_all 初始化；不验证 Alembic 迁移。测试账号 lt_000–lt_039，邮箱 example.com。批次目录、manifest.json 和 requests.json 关联账号、请求、会话；JD 正文不加入标记。
- 真实本机 TCP HTTP/SSE，Uvicorn 单进程；保留认证、聊天路由、SQLite 写入。客户端和服务端共用进程与事件循环，存在测量干扰，不能视为部署容量。
- 模型函数替换为确定性模拟：初始等待 100ms，40 个文本片段，每段前等待 25ms，第二阶段等待 200ms。模拟器随着后端消费推进，不能完全模拟独立上游持续生产及网络缓冲。
- 每轮新建聊天会话、同一份短 JD。1、5、10、20、40 并发，各 3 批；共 228 个计量请求，另 1 个预热和 1 个断流请求。账号注册登录串行预置，不计入容量数据。
- Windows 11，28 个逻辑 CPU，Python 3.13.5。测试针对含既有未提交修改的工作区，不等同某个 Git 提交。

## 已观察问题

1. **数据库锁竞争导致失败。** 20 并发 4 次、40 并发 28 次提交失败；运行期间服务端抛出 sqlite3.OperationalError: database is locked。终端栈包含 UPDATE chat_sessions。此次脚本记录提交耗时及成功标志，未将完整服务端异常栈保存为文件。
2. **HTTP 200 不代表业务完成。** 32 个计量失败请求中，8 个 HTTP 500；24 个 HTTP 200，但没有完整成功结果。这 24 个请求客户端未抛出传输异常，需依靠 done 与内容校验识别失败。
3. **频繁提交与延迟上升同时出现。** 低并发完整请求每轮 44 次提交：创建会话、用户消息、助手占位、40 次片段更新、结构化结果。1 并发提交 P95 为 13.6ms，40 并发为 527.85ms，后者单次最大 7197.82ms。优先优化写入频率值得验证，但当前没有做因果对照实验。
4. **输出存在长时间停顿。** 40 并发时每轮最大片段间隔的 P95 为 5.647 秒，最长 7.046 秒；模拟模型设定间隔仅 25ms。
5. **断流遗留不完整消息。** 单独在收到第 5 段后关闭 HTTP 响应，等待 2 秒读取数据库：保留 155 字符、无 jd_content，会话状态 active，没有每轮中断状态。没有模拟物理断网、恢复网络或自动续传，不能把这个试验称为恢复验收。

## 结论及后续

本轮证明当前实现已在该模拟负载下出现锁竞争、业务中断和不完整消息残留；不能宣布稳定支持 10 并发，也不能把 20 视为固定容量上限。模拟输出没有语义推理，结构正确率不代表真实 JD 解析质量。

建议先降低片段提交频率、补充每轮状态及异常结束协议，再使用相同参数对照复测。后续再扩大持续时间、分离压测端与服务端、增加长 JD/多轮历史/固定到达速率测试，以及独立的真实模型质量评估。

未覆盖：浏览器渲染、真实模型延迟/费用/限流、长时间稳定性、自动恢复、重复提交、多标签竞争、内存峰值、磁盘 I/O、事件循环延迟。CPU 仅记录共享进程的 CPU 时间，未将其当作独立后端利用率。

## 复现及原始数据

在仓库根目录执行：

```powershell
.\backend\.venv\Scripts\python.exe backend/scripts/jd_load_baseline.py
```

每次新建唯一批次目录，不复用现有数据库。保留 synthetic.db 供定位，不自动清理。新一轮不保证与本轮数值完全相同。

- manifest.json：批次、测试用户及环境。
- requests.json：逐请求时延、会话 ID、SSE 和数据库核对结果。
- summary.json：每档聚合；elapsed_ms 包含失败结束时间。
- commits.json：提交耗时与成功标志，包含预置账号阶段；每档统计已排除预置阶段。
- validation.json：数据不一致清单及断流观察。
